# FRONTEND_REBUILD_PLAN.md

## Decision

If the current frontend does not satisfy the product direction, rebuild the frontend from scratch over the existing technical base instead of patching scaffold screens.

The technical base should be preserved:

- Prisma schema and migrations.
- Auth/session/protection logic if working.
- Server-side services, validators and DB utilities.
- `docs/` and `AGENTS.md`.
- Project config required for Next.js, TypeScript, Tailwind and Prisma.

## What to replace

Replace visual scaffold and placeholder UI:

- Generic public home scaffold.
- Placeholder admin pages.
- Temporary admin shell if it does not match the target backoffice.
- Generic Next assets that do not belong to the brand.
- Large static mockup HTML if generated by another tool.

## Safe migration order

1. Create `src/app` and `src/components` structure.
2. Move/replicate auth route to `src/app/api/auth/[...nextauth]/route.ts` if using App Router under `src`.
3. Create global tokens and layout foundations.
4. Create public and admin layout shells.
5. Implement public home with mocks.
6. Implement admin dashboard with mocks.
7. Run lint/build/prisma validate.
8. Only then remove old `app/` tree if its equivalents exist and there are no duplicate route conflicts.

## Do not touch in frontend rebuild tasks

- Do not modify `prisma/schema.prisma` unless explicitly asked.
- Do not delete `prisma/migrations`.
- Do not change the database model.
- Do not rewrite auth unless the task is specifically about auth.
- Do not implement ecommerce.
- Do not connect to WordPress.
- Do not use `rr-management` as runtime backend.
